# Design: Local Docs Sidecar For Manual Ingestion

Generated by plan synthesis on 2026-03-24
Branch: main
Repo: nikolasvoss/ai-debugger-v2
Status: DRAFT

## Problem Statement

DebugOracle helps engineers and agents reason from grounded debug evidence, but many embedded debugging questions still depend on vendor reference manuals and datasheets. Today there is no local, trustworthy way to ingest those PDFs and search them from the same workspace.

The goal of this feature is to add a local `docs` sidecar that lets DebugOracle ingest MCU manuals and datasheets, keep derived artifacts near the source PDFs, and answer document questions with visible quality and provenance signals.

This feature is intentionally a bounded helper for debugging workflows, not a general-purpose PDF knowledge platform.

## What Makes This Cool

The interesting part is not generic document search. It is giving an engineer or agent a sharp local workflow:

- point at a manual or a folder of manuals
- ingest them in-place without cloud dependency
- surface parse quality honestly
- search exact register and peripheral terminology quickly
- keep the derived artifacts portable with the PDFs

That makes DebugOracle better at grounded debugging without diluting the product into a general document tool.

## Constraints

- Local-first and cost-free after installation
- CLI-first
- No hosted retrieval dependency in v1
- Explicit file or folder selection must be supported
- If no explicit input is given, the tool may suggest likely PDFs in `doc/` or `docs/`, but it must not silently ingest them
- Derived artifacts should live next to the source PDFs or in a sibling folder so they can be copied to another project easily
- Search must surface degraded or partial-quality evidence explicitly
- v1 uses keyword/BM25 retrieval only
- Resumable batching is out of scope for the first implementation

## Premises

1. The right v1 problem is not "understand every pixel in a datasheet," but "make a few large MCU PDFs locally usable for grounded debugging questions."
2. Existing document tooling should be reused rather than building a custom PDF parsing stack.
3. Text and tables matter more than diagrams in v1.
4. A separate `docs` subsystem is acceptable in v1 as long as it stays bounded and does not drift into a second product.
5. A tiny canonical envelope is enough to stabilize `docs search` and `docs status` even if parser payloads remain parser-specific.

## Approaches Considered

### Approach A: Workspace-Scoped Local Sidecar

Add a local `docs` subsystem with explicit ingest, nearby derived artifacts, local indexing, and CLI search/status commands.

Pros:
- Best fit for the current DebugOracle product shape
- Local and portable
- Keeps the feature bounded
- Easier to reason about trust and failure states

Cons:
- Adds a parallel subsystem
- Requires new local storage/indexing logic
- Trust/provenance consistency with the rest of DebugOracle must be maintained intentionally

### Approach B: Shared Local Library Across Projects

Build one larger machine-local manual corpus shared across workspaces.

Pros:
- Better reuse across projects
- More ambitious platform direction

Cons:
- Higher indexing complexity
- More wrong-document risk
- Stronger product drift away from the current workspace-oriented workflow

### Approach C: Hosted Hybrid Retrieval

Parse locally but depend on a hosted retrieval layer for search and ranking.

Pros:
- Faster path to broader retrieval sophistication
- Easier future semantic retrieval story

Cons:
- Adds cost and vendor pressure
- Weakens the local-first promise
- Unnecessary for the initial exact-term-heavy MCU manual use case

## Recommended Approach

Choose Approach A: Workspace-Scoped Local Sidecar.

The initial feature should ship as a supported `docs` command group:

- `dbgoracle docs ingest`
- `dbgoracle docs search`
- `dbgoracle docs status`

It should remain separate from the core evidence pipeline in v1, but it should still follow DebugOracle's trust-first posture:

- explicit selection or explicit user confirmation for discovered PDFs
- visible quality reporting
- partial-ingest visibility
- degraded-result warnings
- minimal stable metadata around every ingest

## Architecture

### High-Level Structure

```text
engineer/agent
   |
   v
dbgoracle CLI
   |
   +--> core evidence workflow
   |
   +--> docs subsystem
         |
         +--> docs ingest
         +--> docs search
         +--> docs status
```

### Docs Ingest Flow

```text
source PDF(s)
   |
   +--> explicit file/folder given
   |       |
   |       v
   |    ingest selected input
   |
   +--> no explicit input
           |
           v
     inspect doc/ and docs/
           |
           v
     show likely PDFs
           |
           v
      user confirms selection
           |
           v
        parser run
           |
           +--> parser-specific payloads
           +--> canonical envelope
           +--> nearby derived artifacts
```

### Search And Status Flow

```text
docs search / docs status
   |
   +--> read canonical envelope
   +--> read local index / derived outputs
   +--> apply shared quality-policy rules
   +--> render warnings / degraded state clearly
```

## Data Model

Parser payloads may stay parser-specific in v1, but every ingest must write a tiny canonical envelope with a stable shape.

Minimum envelope fields:

- `source_pdf`
- `parser_used`
- `derived_paths`
- `page_count`
- `chunk_count`
- `warning_summary`
- `ingest_state`: `clean | warning | partial | failed`

This envelope is the contract `docs search` and `docs status` rely on.

## Quality Policy

One shared quality-policy source should define:

- how parser warnings map to severity
- what counts as degraded evidence
- when an ingest is `warning`, `partial`, or `failed`
- what `docs search` must surface on degraded results
- what `docs status` must surface about parser quality and fallback use

This avoids duplicating quality logic across commands.

## CLI Contract

### `dbgoracle docs ingest`

Responsibilities:

- accept explicit file selection
- accept explicit folder selection
- if no input is given, inspect `doc/` and `docs/` and propose likely PDFs
- show progress while ingesting
- emit an explicit quality result
- write nearby derived artifacts and canonical envelope

### `dbgoracle docs search`

Responsibilities:

- query the local BM25 index
- return exact-term-friendly results for registers, peripherals, and datasheet terminology
- surface degraded-result warnings when relevant

### `dbgoracle docs status`

Responsibilities:

- report current or last ingest health
- display parser used, warnings, and ingest state
- indicate whether artifacts are missing, partial, or degraded

## Test Plan

The implementation should include a committed regression corpus made of trimmed representative real-document pages plus focused synthetic edge-case fixtures.

Required coverage:

- explicit file ingest
- explicit folder ingest
- discovery flow from `doc/` and `docs/`
- empty discovery result
- clean ingest
- ingest with warnings
- partial ingest
- failed ingest
- canonical envelope generation
- search hit on clean chunk
- search hit on degraded chunk with warning
- zero-result search
- missing or corrupt envelope/index handling
- status output for `clean`, `warning`, `partial`, and `failed`

Representative fixture mix:

- prose pages
- multi-column pages
- table-heavy register pages
- ugly/problem pages
- malformed or parser-hostile sample

## Risks

- Parser-specific payloads will create normalization debt later if multiple fallback parsers grow in importance.
- Keeping `docs` separate from the core evidence workflow can create product drift if the boundary is not maintained.
- Without resumable batching, large or ugly PDFs remain a known ingest limitation even with visible progress.
- A minimal persistent status model is weaker than a full ingest flight recorder for long-term debugging.

## Failure Modes

- malformed PDF
  - expected behavior: visible failure or partial state, never silent success
- parser returns weak output
  - expected behavior: warning or degraded state
- some pages fail while others parse
  - expected behavior: partial ingest with explicit page/chunk-level visibility
- degraded chunk retrieved during search
  - expected behavior: result still shown, but warned
- missing or corrupt canonical envelope or index
  - expected behavior: clear `docs status` or `docs search` error, not a silent empty result

## Not In Scope

- semantic retrieval in v1
- target-binding to the exact MCU/project in v1
- hosted retrieval
- resumable batching
- full parser-output normalization
- a rich persisted ingest flight-recorder artifact
- turning the docs subsystem into a broader knowledge platform
